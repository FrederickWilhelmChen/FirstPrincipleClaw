# FirstClaw x OpenClaw 集成设计结论

## 文档目的

沉淀此前关于 FirstClaw 与 OpenClaw 集成方式、交互策略、平台取舍的结论，作为后续实现和产品决策的基线。

这份文档不讨论具体代码实现，而是回答三个问题：

1. FirstClaw 要以什么形态嵌入 OpenClaw
2. 哪些交互是主线体验，哪些是增强体验
3. 如何同时兼顾 macOS 和 Windows 用户

---

## 核心结论

### 1. 不把产品核心价值绑定在 Canvas 上

OpenClaw 的 Canvas 能提供非常理想的伴随式体验，但当前属于 macOS 原生能力，不适合作为 FirstClaw 的唯一主交互。

原因很直接：

- Windows 用户体量很大，不能成为降级用户
- 如果核心体验依赖 Canvas，Windows 用户天然缺失“背景板”能力
- 产品的核心价值应该建立在跨平台能力上，而不是平台专属壳能力上

因此，Canvas 只能定义为增强层，不应定义为主线能力。

### 2. Windows 必须是主平台之一，而不是兼容平台

FirstClaw 的目标不是做一个“在 macOS 上很好、在 Windows 上凑合”的功能，而是做一个真正跨平台可用的思维背景板。

因此产品策略必须是：

- 跨平台能力负责交付完整核心体验
- 平台专属能力负责增强体验

这意味着：

- Windows 要有完整的主线交互
- macOS 可以在此基础上进一步获得更丝滑的伴随式体验

### 3. FirstClaw 应采用“两层交互”

最合理的交互结构不是单独一个大看板，而是两层：

- 轻提示层：嵌入 OpenClaw 会话流，低打扰、短反馈
- 深查看层：独立面板或独立 UI，承载完整分析、历史和操作

这比“永远盯着仪表盘”更符合真实使用路径。

---

## 我们已经明确的产品判断

## FirstClaw 的真实角色

FirstClaw 不是另一个 Agent，也不是大型多 Agent 编排系统。

它更像：

- 思维的背景板
- 复杂度的提醒器
- 最简方案的辅助提炼器

它的职责不是替用户完成任务，而是在用户与 OpenClaw 协作时，持续指出：

- 当前复杂度是否升高
- 复杂度来自哪些隐含假设
- 哪些部分可以砍掉
- 当前任务的最简方案是什么

因此，它的交互应该服务“提醒”和“决策”，而不是服务“展示一堆数据”。

---

## OpenClaw 集成能力判断

根据当前调研，OpenClaw 已经具备足够多的接入点来支持 FirstClaw 的主线体验。

### 已确认可利用的能力

1. `bootstrap-extra-files`
   可用于注入 `MEMORY.md`、`SOUL.md` 这类上下文文件，适合放 FirstClaw 的分析约束和规则。

2. Hook 机制
   可用于在启动、会话开始、任务切换等时机触发分析逻辑。

3. Plugin 机制
   可注册 hook、工具、命令、HTTP route、后台服务，适合将 FirstClaw 从“仓库外挂脚本”升级为 OpenClaw 插件。

4. `chat.inject`
   可向当前 transcript 注入一条 UI 消息，而不触发完整 agent run。
   这是实现“轻提示层”的关键能力。

5. Gateway / Control UI
   可作为现成宿主，承接会话流、状态流和外部链接。

6. Canvas
   适合做伴随式浮层或小型交互界面，但当前只适合作为 macOS 增强能力。

### 尚未确认或不应预设的能力

1. 不能预设 OpenClaw 现有 Control UI 支持任意业务模块直接原生插槽化
2. 不能预设 Windows 端存在等价于 macOS Canvas 的原生伴随 UI
3. 不能预设用户愿意长期额外打开一个复杂的独立仪表盘

因此设计上应默认：

- 聊天流中的轻提示一定要存在
- 深度分析可以放在独立 UI
- Canvas 只做增强，不做依赖

## 集成契约

## 系统边界

FirstClaw 与 OpenClaw 的职责边界必须明确，避免后续实现中出现双写、重复判断或交互职责混乱。

### OpenClaw 负责

- 决定什么时候触发 FirstClaw 分析
- 提供会话上下文和 session 标识
- 通过 `chat.inject` 将轻提示送入当前 transcript
- 承载用户当前工作流，不要求用户离开主会话就能感知提醒

### FirstClaw 负责

- 基于上下文产出结构化第一性原理分析结果
- 维护当前分析状态和历史记录
- 生成轻提示所需的压缩消息载荷
- 提供深查看页面和动作闭环

### Transcript 与 Panel 的边界

- OpenClaw transcript 只显示短提示，不显示整篇分析
- FirstClaw panel 承载完整分析、状态、历史和操作按钮
- transcript 负责“让用户知道现在值得看”
- panel 负责“让用户理解原因并完成动作”

## 轻提示消息载荷

所有层统一使用同一份轻提示消息结构，避免运行时再做二次猜测。

```json
{
  "session_id": "oc_session_123",
  "task": "Implement login flow",
  "complexity": 78,
  "delta": 12,
  "top_reasons": [
    "Added OAuth",
    "Assumed multi-tenant support"
  ],
  "can_remove": [
    "OAuth",
    "multi-tenant"
  ],
  "deep_view_url": "http://127.0.0.1:5000/?session=oc_session_123",
  "status": "updated"
}
```

### 字段约束

- `session_id`
  OpenClaw 当前会话唯一标识。
- `task`
  当前任务的简短描述。
- `complexity`
  当前复杂度分值，范围 `0-100`。
- `delta`
  相比上一次分析的复杂度变化量，可为负数。
- `top_reasons`
  本次提示最重要的 1 到 3 个原因。
- `can_remove`
  当前建议砍掉的条目列表。
- `deep_view_url`
  指向深查看页的直接链接。
- `status`
  当前提示状态，只允许：
  - `waiting`
  - `updated`
  - `failed`
  - `stale`

## `chat.inject` 通知规则

轻提示不是每次分析都发，必须有明确的准入条件。

### 允许注入的场景

1. 某个 session 第一次成功完成分析
2. 复杂度上升超过阈值
3. `can_remove` 集合出现明显变化
4. 用户显式要求“简化一下”或“用第一性原理看看”

### 不应注入的场景

1. 本次分析与上次结果实质相同
2. 只是时间戳变化，没有内容变化
3. 当前状态为 `failed`
4. 当前状态为 `stale`
5. 刚刚已经发送过相同提示，处于去重窗口内

## 轻提示文案原则

轻提示必须回答三个问题：

1. 发生了什么
2. 为什么值得看
3. 去哪里看

推荐文案结构：

- `复杂度升至 78，新增 2 个隐含假设。查看分析`
- `建议砍掉 OAuth、多租户。查看分析`
- `最简方案已更新。查看分析`

不推荐：

- 大段 reasoning
- 过长列表
- 没有下一步动作的提示

## 推荐的集成结构

## 结构总览

FirstClaw 与 OpenClaw 的集成分为三层：

1. 分析触发层
2. 轻提示层
3. 深查看层

### 1. 分析触发层

目标：在恰当时机静默完成第一性原理分析。

推荐使用：

- `bootstrap-extra-files` 注入分析规则
- Hook 或 Plugin 触发分析
- 脚本或服务写入结构化分析结果

职责：

- 提取用户真正意图
- 识别隐含假设
- 估算复杂度变化
- 生成可砍掉项和最简方案

### 2. 轻提示层

目标：用户不离开 OpenClaw，也能感知 FirstClaw 的价值。

推荐使用：

- `chat.inject`

表现形式应尽量短：

- “复杂度升高到 78，新增 3 个隐含假设”
- “建议砍掉：OAuth、多租户、审计日志”
- “最简方案已生成，点击查看”

这层的原则是：

- 信息短
- 不抢主任务焦点
- 只有变化时才提示
- 能把用户引导到深查看层

### 3. 深查看层

目标：让用户理解原因并完成动作闭环。

推荐使用：

- 独立 Web 面板
- 独立本地页面
- 后续可选 macOS Canvas

深查看层承载：

- 真实意图
- 隐含假设
- 客观事实
- 推导过程
- 可砍掉项
- 最简方案
- 历史趋势

更重要的是，这一层必须有动作，而不是只有信息：

- 复制最简方案
- 标记某项建议已采纳
- 忽略某项建议
- 把最简方案回注到当前会话

---

## 为什么“两层交互”比“单独看板”更顺

如果只有独立看板，会出现几个问题：

- 用户需要自己切过去看
- 用户无法确定系统是否刚刚分析过
- 用户必须先理解仪表盘，再理解建议
- 看板容易沦为演示界面，而非真实工作界面

两层交互的优势在于：

- 轻提示先告诉用户“现在值得看”
- 深查看再解释“为什么”和“怎么做”
- 用户决策路径更短
- 系统存在感更自然

也就是说，FirstClaw 不应该要求用户一直盯着面板，而应该在真正有变化时出现。

## Windows 体验策略

## 基本原则

Windows 用户必须拥有完整的主线体验。

主线体验至少包括：

1. 在 OpenClaw 会话中收到轻提示
2. 一键打开深查看面板
3. 看到明确的系统状态
4. 能完成最关键的操作闭环

### Windows 端必须做好的四件事

1. 会话内可见
   用户不应必须切到外部看板，才能知道系统有建议。

2. 一键可达
   轻提示必须能直接打开对应分析页。

3. 状态清晰
   至少需要区分：
   - 等待分析
   - 已更新
   - 分析失败
   - 数据过旧

4. 动作闭环
   用户必须能：
   - 复制最简方案
   - 忽略提示
   - 接受建议
   - 回注到当前对话

### 不应接受的 Windows 体验

- 只能看外部网页，没有会话内提示
- 功能上缺失“背景板”核心价值
- 明显依赖 macOS 才成立
- 只有演示效果，没有工作流闭环

---

## macOS 体验策略

macOS 应作为增强层，而不是另一个完全不同的产品分支。

建议定义为：

- 核心能力与 Windows 一致
- 在此基础上增加 Canvas 浮层能力

Canvas 可以额外提供：

- 更像状态栏的伴随式可见性
- 更低打扰的浮层
- 更快的打开和关闭

但不应承担只有它才能实现的关键能力。

## 交互设计结论

## 当前交互问题

如果 FirstClaw 只是一个静态看板，会有三个明显问题：

1. 价值出现太晚
   用户必须主动查看，才知道系统有帮助。

2. 缺少信任反馈
   用户不知道系统是否刚刚分析、分析了什么、为什么提示。

3. 缺少动作闭环
   用户看到建议后，没有快速处理路径。

## 推荐的交互顺序

更顺滑的交互应该是：

1. 用户进行任务
2. 系统静默分析
3. 会话中出现轻提示
4. 用户点击进入深查看
5. 用户执行动作
6. 结果再回到当前工作流

## 深查看页优先级

深查看页的内容顺序建议为：

1. 你真正要做什么
2. 为什么现在复杂
3. 可以砍掉什么
4. 最简方案是什么
5. 推导过程
6. 历史记录

这里的关键是：

- 先给结论
- 再给原因
- 最后给过程

而不是一上来让用户读完整 reasoning。

## 推荐路线

## 推荐路线 A：跨平台主线方案

这是当前最推荐的方案。

组成：

- `bootstrap-extra-files`
- Hook / Plugin
- `chat.inject`
- 独立 Web 面板

优点：

- 跨平台
- 与 OpenClaw 现有能力最贴合
- 实现风险最低
- 最适合做 MVP

缺点：

- 伴随感不如原生 Canvas 强
- 深查看仍然需要单独 UI

## 推荐路线 B：插件化增强方案

在路线 A 的基础上，逐步把 FirstClaw 收拢为 OpenClaw 插件。

适合在 MVP 验证后推进。

优点：

- 架构更内聚
- 更像 OpenClaw 原生能力
- 后续扩展 hook、工具、服务更自然

缺点：

- 实现复杂度更高
- 需要更清晰的插件边界设计

## 推荐路线 C：macOS Canvas 增强方案

在路线 A 或 B 稳定后，作为 macOS 增强项追加。

优点：

- 伴随感最好
- 最接近“思维背景板”的理想体验

缺点：

- 仅限 macOS
- 不可作为核心能力依赖

---

## 最终决策

当前阶段的最终结论如下：

1. FirstClaw 的主线体验必须跨平台成立
2. Windows 是主平台之一，不是降级平台
3. OpenClaw 的现有能力足以支撑主线方案
4. 主线交互采用“两层交互”：轻提示 + 深查看
5. `chat.inject` 是最关键的轻提示接入点
6. 独立 Web 面板是当前最现实的深查看承载方式
7. Canvas 仅作为 macOS 增强项，不作为核心依赖

---

## 后续实现建议

后续若进入实现阶段，建议按以下顺序推进：

1. 先定义轻提示消息结构
2. 再定义深查看面板的数据结构
3. 然后确定 Hook / Plugin 的触发时机
4. 最后再考虑 macOS Canvas 的增强实现

实现顺序上，优先交付：

- 跨平台主线体验
- 会话内轻提示
- 深查看动作闭环

延后交付：

- macOS 专属浮层
- 更复杂的视觉动画
- 更重的原生壳集成

这样能最大程度降低架构押注风险，同时保证产品价值尽快成立。
